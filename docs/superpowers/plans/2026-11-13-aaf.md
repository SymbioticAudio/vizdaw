# AAF Implementation Plan (6f)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** AAF import and export for DAW-to-DAW exchange. Export writes a folder "<Song> AAF" holding `<Song>.aaf` (Edit Protocol, 4 KiB sectors, audio embedded by default), `<Song> MIDI.mid` beside it when the sequence has MIDI, and `Audio/` when the audio is external. Import opens an AAF as a new project (or adds it to this one) with its clips, fades, crossfades, clip gain, track volume and pan, markers and names, and with the MIDI file beside it for bars and MIDI tracks. Clips that point at MXF arrive offline. Everything changed or left out is listed, and hostile files never crash, hang or fill the disk.

**Architecture:**
- **`core-io::aaf`**, our own reader and writer on `cfb` (spec §5, owner):
  - `store`: the AAF object store over the compound file. It reads and writes objects, properties, strong references (single, vector, set), weak references and data streams, within the §6.5 limits;
  - `dict`: the class, property and definition IDs we use;
  - `timeline`: the top-level composition read into a neutral `Composition` (slots, clips, transitions, gain, pan, markers, timecode, media);
  - `import`: a `Composition` mapped to **6d's import plan** (`DpImport`), then applied by 6d's `apply_tracks` and `arrange_tracks`;
  - `export`: a document mapped to an object tree plus the audio to stage, and that tree written with the essence streamed in.
- **Reuse, not rebuild.** These are 6d's and 6e's pieces, used as they are or widened with one parameter:
  - the report, the limits module, `read::open_regular`, `write::{free_folder, stage_folder}`, `names::safe_part` and `text::sanitize`;
  - 6d's plan, `apply_tracks`/`arrange_tracks` (6e made them work on a project that has tracks), `MediaSource`, `AudioRef` and `AudioSource`;
  - the job's `read_and_convert` (free space, extraction, conversion, offline media);
  - `stage_audio` (a WAV from a media CAF), `capture`-free export checks, `interchange_idle`, `report_row` and `file_path`;
  - 6a's `midi_in::{parse, apply}` and `midi_out::to_smf_until`, with 6b's `for_daw::midi_tracks`;
  - the Swift job queueing (`ForDawModel.blocking`), `DawprojectModel`'s detached check with its generation counter, `ReportSheet`, `InterchangeCommands`' `.pending` read-first pattern and `madeProjects`.
- **`core-ffi`** gains `aaf.rs`: an `ExportAaf` job and an `ImportAaf` job, the info read (a free function, as `dawproject_info`) and the session methods.

**The storage facts the plan relies on** (Low-Level Container Specification; LibAAF's `AAFTypes.h`/`AAFCore.c` agree). The implementer checks every field against the specification before coding:
- **Objects.**
  - Each object is a storage whose CLSID is its class AUID.
  - Its properties are in a stream named `properties`:
    - a header of `byteOrder` (u8, `0x4C` 'L' little-endian), `formatVersion` (u8, write `0x20`) and `entryCount` (u16);
    - then `entryCount` entries of `pid` (u16), `storedForm` (u16) and `length` (u16);
    - then the values, concatenated in entry order.
- **Stored forms:**

  | Form | Value |
  |---|---|
  | data | `0x82` |
  | data stream | `0x42` |
  | strong reference | `0x22` |
  | strong reference vector | `0x32` |
  | strong reference set | `0x3A` |
  | weak reference | `0x02` |
  | weak reference vector | `0x12` |
  | weak reference set | `0x1A` |
  | weak reference, stored object ID | `0x03` |
  | unique object ID | `0x86` |
  | opaque stream | `0x40` |
- **Strong references.** A strong reference's value is the UTF-16LE, NUL-terminated name of a child storage. A vector or set value names an index stream `<name> index`:
  - **vector index:** `entryCount`, `firstFreeKey` and `lastFreeKey` (u32 each), then one u32 `localKey` per entry;
  - **set index:** the same three u32 fields, then `identificationPid` (u16) and `identificationSize` (u8), then entries of `localKey` (u32), `referenceCount` (u32) and the identification bytes.

  Element `i` is the storage `<name>{<localKey in lowercase hex>}`.
- **Weak references.** A weak reference holds `referencedPropertyIndex` (u16), `identificationPid` (u16), `identificationSize` (u8) and the identification bytes, usually a 16-byte AUID. The index points into the root's `referenced properties` stream (a table of property paths).
- **Data streams.** A data stream property's value is a stream name. `EssenceData`'s `Data` (pid `0x2702`) is the stream `Data-2702`.
- **Essence.**
  - An embedded `WAVEDescriptor` essence is a whole WAV file. Its `Summary` holds that file's header chunks.
  - An `AIFCDescriptor` essence is a whole AIFC file.
  - A `PCMDescriptor` essence is raw interleaved little-endian PCM.
- **Definition AUIDs** used by name below:

  | Name | AUID |
  |---|---|
  | `DataDef_Sound` | `01030202-0200-0000-060e-2b3404010101` |
  | `DataDef_Timecode` | `01030201-0100-0000-060e-2b3404010101` |
  | `DataDef_DescriptiveMetadata` | `01030201-1000-0000-060e-2b3404010101` |

## Review Focus

These are the five failure modes a user is most likely to hit, most likely first. Each is pinned by named tests in its task.

1. **A file from another DAW built in shapes we never write.**
   - Examples:
     - a composition at 25 fps whose clips point into 48 kHz sources;
     - nested `Sequence`s;
     - two `MonoAudioGain` groups nested around one clip;
     - a `Transition` with no `CutPoint`;
     - fades stored as `SourceClip` fade properties instead of transitions;
     - several `CompositionMob`s with none marked top-level;
     - a sub-composition used as a clip;
     - a `Selector` or `EssenceGroup`;
     - a mono slot that plays channel 2 of a stereo file;
     - slots of picture or timecode data.
   - Expected: every audio clip plays where it played there, within a sample. What VizDAW cannot hold is listed.
   - Pinned by Task 2's `reads_other_shapes` group and Task 3's `positions_at_other_edit_rates`.
2. **Media that cannot be read where the file says.**
   - Examples:
     - MXF essence;
     - a `file://host/C:/x.wav` locator;
     - a percent-encoded or relative `../` locator;
     - a locator to a FIFO or a folder;
     - an `http://` locator;
     - a `PCMDescriptor` with raw data;
     - a big-endian AIFC;
     - essence shorter than its descriptor says;
     - a 6-channel file.
   - Expected:
     - unreadable media becomes offline regions with relink, listed;
     - a file found by name in the chosen media folder is used;
     - nothing is fetched or written outside `Media/`.
   - Pinned by Task 2's `media_refs_resolve_or_go_offline` and Task 5's `offline_and_found_media` (macOS).
3. **A hostile compound file.**
   - Examples:
     - cyclic FAT or directory chains;
     - a strong reference that names its parent;
     - 65 deep references;
     - a vector index claiming 2³² entries;
     - a weak reference past the referenced-properties table;
     - property lengths past the stream;
     - mob chains that loop (A → B → A);
     - an odd-length UTF-16 string;
     - a 4 GiB declared essence in a 1 KiB file;
     - a byte-flipped golden.
   - Expected: refused in one sentence, or imported with the bad items listed. Never a panic, never `Internal`, and each case under 2 s and 256 MiB.
   - Pinned by Task 1's store tests, Task 7's `aaf_fuzz.rs` (4096 cases) and `aaf_limits.rs`.
4. **VizDAW shapes on the way out and back.**
   - Examples:
     - a crossfade;
     - overlapping regions with no crossfade;
     - each fade shape;
     - region gain;
     - a muted region;
     - a pickup before bar 1;
     - a tempo ramp (it reaches the MIDI file);
     - a stereo region written as mono pairs;
     - fader and pan automation;
     - a track with notes and audio.
   - Expected: after export and import, the projection is equal within the stated tolerance (one sample, the same ticks), and the report lists exactly the expected kinds.
   - Pinned by Task 4's `round_trips_preserve_the_projection` and its fixed cases.
5. **Names and text.**
   - Examples:
     - UTF-16 with unpaired surrogates or no NUL;
     - a 70 000-character slot name;
     - names with `/`, NUL and bidirectional overrides;
     - L/R names written "Gtr L", "Gtr.L", "Gtr Left" and "Gtr.R";
     - a track named just "L";
     - two pairs with one stem;
     - pairs whose clip layouts differ by one sample.
   - Expected:
     - text is sanitised and cut with a Changed line;
     - only true pairs with identical layouts join;
     - everything else stays mono and gets a Note.
   - Pinned by Task 2's `strings_are_sanitised` and Task 3's `pairs_join_only_when_identical`.

## Plan Rulings

These are this plan's decisions where the spec leaves a choice. Each names its cost if wrong.

1. **The composition we read.**
   - The first `CompositionMob` whose `UsageCode` is `Usage_TopLevel`.
   - Else the one no other mob references.
   - Else the first in `ContentStorage` order.

   More than one candidate gets a Note, "The file holds several compositions; the first top-level one was imported".

   Slots are `TimelineMobSlot`s with `DataDef_Sound` (also its legacy AUID), in slot order. One `Timecode` slot gives the start. `EventMobSlot`s with `DescriptiveMarker`s give the markers. Picture and other data slots are Left out, "Picture and other non-audio tracks".

   *Cost if wrong:* choosing the composition is one function.
2. **Export folder and names.**
   - `path` is the folder the export folder goes in, as for 6b. The export folder is `free_folder(path, "<Song> AAF")`, so an existing one gets " 2" and is never replaced. The spec's `replace` parameter is not added (owner question 1).
   - Inside it:
     - `<Song>.aaf`;
     - `<Song> MIDI.mid`;
     - `Audio/NNN <name>.wav` (from 001, in write order; only when external).
   - `<Song>` is `safe_part(sequence name, …)`, else "Untitled".
   - Everything is staged in `.<Song> AAF.partial` (`stage_folder`) and committed at the end.

   *Cost if wrong:* if the owner wants replace, `PendingFolder` gains a swap.
3. **Edit rates and positions (spec §7.5 "Positions").**
   - **Export:** every slot's `EditRate` is the project's sample rate, `Origin` is 0, and every length and position is in frames.
   - **Import:** a position `p` at edit rate `n/d` is `p·d/n` seconds, computed with `i128`. VizDAW's tick is `seconds_to_tick` on the plan's tempo map, measured from the sequence's `midi_out::file_start`.
     - Source offsets convert at the source slot's own rate to frames at the media's rate, rounding half up.
     - The report says Changed, "Positions moved to VizDAW's resolution by more than one sample", only when a region's start (converted back through the same map) is more than one frame away.
   - **The start timecode** is metadata. Composition position 0 is the song's start, and the timecode value only sets the `Timecode` component (export) or is noted (import: "The file's timecode starts at <tc>; it was placed at the start of the song").

   *Cost if wrong:* one conversion function per direction.
4. **The sequence layout we write and read.** A slot's `Sequence` is placed left to right. A `SourceClip`, `Filler` or `OperationGroup` advances the position by its `Length`; a `Transition` moves it back by its own `Length` (it overlaps both neighbours).
   - **Fade-in** (no crossfade): `Filler(gap + L)`, `Transition(L)`, clip. **Fade-out:** clip, `Transition(L)`, `Filler(L + gap)`. The filler gets the `L` the transition takes back, so butted clips and a clip at 0 still work.
   - **Crossfade** of B over A with fade-in `L`: A cut to end at `B.start + L`, then `Transition(L, CutPoint 0)`, then B. With `CutPoint 0`, a reader that ignores transitions cuts where VizDAW's later region takes over.
   - **Transition contents:** an `OperationGroup` of `OperationDef_MonoAudioDissolve` whose `Level` is a `VaryingValue` from (0, 0) to (1, 1), with the shape as its `Interpolation`.
   - **Overlaps with no crossfade** (the later start takes over): the earlier region is written up to the later start. If the earlier one plays on after the later one ends, the rest is written after it as a second clip with its `StartTime` moved on. An earlier fade-out cut short this way is Changed, "Fade-outs under a later region were cut".
   - **Import** reads the same layout. It also reads `SourceClip` `FadeInLength`/`FadeInType`/`FadeOutLength`/`FadeOutType` when no transition gives the fade. Nested `Sequence`s are flattened.

   *Cost if wrong:* the layout is one walker each way; a reader that needs `CutPoint = L/2` changes one constant.
5. **Fade shapes.**

   | VizDAW | AAF interpolation | Back on import | Report on export |

7. **Stereo.**
   - **Export:** with `mono_pairs` (the default), a stereo track becomes two slots, "<track> L" and "<track> R". Each plays one mono WAV, staged per channel. With `stereo`, the track is one 2-channel slot and file. Mono tracks are one slot either way.

     - their names differ only in a suffix pair, `" L"/" R"`, `".L"/".R"` or `" Left"/" Right"` (case-insensitive);
     - both are mono;
     - their clips match one for one in position, length, offset, fades and gain;
     - the paired media items have the same rate and frame count.

    - **Structure:**
      - `MAX_AAF_OBJECTS` 1 000 000;
      - `MAX_REF_DEPTH` 64;
      - `MAX_PROPERTIES_BYTES` 1 MiB per `properties` stream;
      - `MAX_INDEX_ENTRIES` 1 000 000 per index;
      - `MAX_MOB_CHAIN` 16, walked with a visited set of MobIDs;
      - `MAX_CONTROL_POINTS` 100 000 per curve;
    - **Text:** `MAX_TEXT_BYTES` per string;
    - **Tracks:** 6d's `MAX_IMPORT_TRACKS`;
    - **Memory:** a model budget of 6d's `MAX_MODEL_BYTES`, counted as objects are read.

    Every count and offset in an index or property is checked against its stream's real length before anything is allocated. A declared essence length must fit its stream.

    **Refusals of the whole file:**
    - not a compound file;
    - a bad header, FAT or directory (`cfb`'s errors);
    - big-endian `properties` ('B'): "This AAF file is big-endian; VizDAW reads little-endian files";
    - no `Header` or no composition;
    - the object, depth or budget limits.

    **Items left out and listed:**
    - one damaged object;
    - a dangling weak reference;
    - a mob chain that loops or runs too deep;
    - a bad rational.

    **A panic inside `cfb`** is caught in `store::read` and becomes "This AAF file is damaged" (it is upstream's bug; the fuzz task reports any it finds).

    *Cost if wrong:* constants.
