# VizDAW Tracks — The Usability Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the arrangement usable from a new project.
- The editor views stop painting over the track headers and the arrangement bar, and `ui.screenshot` stops hiding that kind of fault.
- New projects open on "Sequence 1".
- "Lane" reads "Track" everywhere a user sees it.
- A Track menu, a kind icon on each header, and Add Track in the Mix view.

**Architecture:**
- **`core-model`:** two new commands. `LaneCmd::Duplicate` copies a track. `RoutingCmd::AddOutput` adds an output path when the document has none. No model type or file format changes.
- **`core-ffi`:**
  - `crates/core-ffi/src/tracks.rs` (new) holds `TrackKindRow`, `track_kind`, `Session::new_track` and `Session::duplicate_track`. `new_track` builds a track from existing commands in one history transaction.
  - `LaneRow` gains `kind`.
  - `new_empty` and `new_project` start with "Sequence 1".
  - `ControlRequest::Screenshot` gains `live`.
- **`core-control`:** six `track.*` commands (registry 157 → 163), `ui.screenshot`'s `live` parameter, and the Rust "Lane" scans.
- **`VizDAWEditors`:**
  - every NSView subclass clips to its bounds;
  - `WindowSnapshot` clips as the window server does;
  - the header shows the kind icon, and its "+ Add Track" row opens a menu.
- **`VizDAWAppModel`:** `TrackCommands`, the "Track" wording, and the clip and wording scans.
- **`VizDAW`:**
  - the Track menu;
  - the "No Sequence" state's New Sequence button;
  - Mix's Add Track;
  - the live screenshot, through ScreenCaptureKit.

**Tech Stack:** Rust 2024 (UniFFI 0.32.2); Swift 6 / SwiftPM (Swift Testing; SwiftUI and AppKit), macOS 14+; `symbiotic-design` 0.2.2 (unchanged pin); ScreenCaptureKit (system framework, autolinked).

**Spec:** the owner's approval of 2026-11-05, items 1–6, recorded in Plan Rulings 1–7, and the clipping diagnosis summarised in Ruling 1. The diagnosis itself is in a session scratchpad and is not in the repo: Ruling 1 carries what it found.

Out of scope:
- renaming code identifiers, `lane.*` command ids, FFI names or file keys;
- reordering tracks by drag;
- track folders;
- the Linux app.

## Review Focus

These are the five failure modes a user is most likely to hit that the owner's scope implies but no feature test exercises, most likely first. Each is pinned by the named tests in its task.

1. **A view that still paints outside its frame.**
   - The cases:
     - the ruler's labels left of bar 1;
     - a header scrolled vertically past the add row;
     - the drum grid's, piano roll's and strip chart's canvases (`EditorCanvas` subclasses);
     - a view added later without `clipsToBounds`.
   - Expected: nothing paints over a sibling, and the scan fails on a new view that does not clip.
   - Pinned by `everyViewSubclassClipsToItsBounds` and `theHeadersAndAddRowShowBesideTheCanvas` (Task 1).
2. **Old projects and scripts after the rename.**
   - The cases:
     - a project whose tracks are named "Lane 1";
     - a keys file that binds `lane.track_synth`;
     - `command.run lane.set_input`;
     - a `"lanes"` key in state answers;
     - a typed "lane" in a list cell's track column.
   - Expected: all of these work unchanged. Only text the app shows changes.
   - Pinned by `noLaneInWhatTheAppShows` (Task 3, which also asserts that the kept ids still parse), the existing `core-ffi/tests/format.rs`, and the e2e's `lane.track_synth` (`tracks_the_fake_synth`, Task 5).
3. **Creating a track in a thin document.**
   - The cases:
     - New Instrument Track with no built-in synth destination yet;
     - New Audio Track with no output path;
     - New MIDI Track with no external destination;
     - each of these with no sequence selected, while recording, or with an edit open.
   - Expected:
     - the synth destination or the output path is created inside the same undo step, and one Undo removes everything;
     - a MIDI track with no external destination is made with no destination, and the status line says so (Ruling 4);
     - with no sequence the items are disabled and the channel refuses "select a sequence first";
     - while recording or with an edit open, the call is refused with Busy.
   - Pinned by `new_track_makes_each_kind_in_one_undo_step`, `a_midi_track_with_no_external_destination_has_none` and `new_track_refuses_unknown_ids_and_busy` (Task 2), and `trackItemsNeedASequence` (Task 4).
4. **New default keys taking a user's key.**
   - The cases:
     - a keys file that gives ⌥⌘A, ⌥⌘S or ⌥⌘X to another command;
     - a saved sequence keyboard slot on one of them.
   - Expected: the user's binding keeps the key, and the new command starts unbound there (`yields: true`, 7d controller ruling I3).
   - Pinned by `a_keys_file_key_wins_over_the_track_defaults` (Task 2) and `aSavedBindingKeepsItsKeyOverTheTrackDefaults` (Task 4).
5. **Duplicate and Delete on a busy track.**
   - The cases:
     - Duplicate a track with takes, a drum layout, audio regions and a reference region;
     - Delete the only track;
     - Delete or Duplicate while recording;
     - Rename to an empty name.
   - Expected:
     - Duplicate copies every take, event and region with fresh ids below the original, named "‹name› copy", with the source's routing and flags but disarmed;
     - deleting the only track leaves an empty sequence with the "+ Add Track" row;
     - while recording: Busy, said in the status line;
     - an empty name is refused by the existing rename rule.
   - Pinned by `duplicate_track_copies_takes_with_fresh_ids` (Task 2), and `deleteTheOnlyTrackLeavesTheAddRow` and `renameTrackStartsTheHeadersField` (Task 4).

## Plan Rulings

Each ruling decides something the owner's scope leaves to the builder, as "what — why — cost if wrong". The owner's six items of 2026-11-05 bind.

1. **Ruling (clipping, owner item 1).**
   - **What the diagnosis found** (the model is fine):
     - No view in `app/Sources` sets `clipsToBounds`, and the deployment target, macOS 14, defaults it to false.
     - `EditorCanvas`'s grid, content, overlay and ruler `CanvasLayerView`s fill their dirty rects and draw ruler marks from `dirty.minX - 60` (`EditorCanvas.swift` `drawGrid` and `drawRuler`). So bar "0" lands at a negative x, over the header column and the arrangement bar.
     - `ArrangementContainer` adds `headers`, then `canvas`, so the canvas paints on top of `LaneHeaderView`.
     - `WindowSnapshot.redraw` clips each self-drawn view to `visibleRect ∩ bounds`, so `ui.screenshot` hid the fault.
   - **What changes:**
     - Every NSView subclass in `app/Sources` sets `clipsToBounds = true` in each of its initializers, or inherits it from a scanned superclass that does.
     - The scan's allow-list is AppKit controls whose focus ring sits outside their bounds: `TransportTextField`, `ListCellField` and `HoldButtonView`. Each has a one-line reason in the scan. A control that draws itself (`draw(_:)` override) cannot be listed.
   - Why: owner item 1, applied app-wide.
   - Cost if wrong: a clipped focus ring or a cut-off shadow, which README 233 checks.
2. **Ruling (`ui.screenshot`, owner item 1): the default stays app-drawn but clips as the window server does, and `live: true` is opt-in.**
   - **Why there is no live default:**
     - `CGWindowListCreateImage` is obsoleted in the macOS 15 SDK, which CI's Swift 6.1 builds against, so it does not compile there.
     - ScreenCaptureKit (`SCShareableContent`, `SCScreenshotManager.captureImage`, macOS 14) needs Screen Recording permission, even for the app's own windows, and asks for it on first use.
     - A test must never prompt. So the default stays the app's own rendering, and live capture is opt-in.
   - **The default, made faithful:** `WindowSnapshot.redraw` clips each view to `WindowSnapshot.clipRect(of:in:)`. That is the intersection, in root coordinates, of the root's bounds with the bounds of the view and of each ancestor that clips (`clipsToBounds`, or `NSClipView`). The redraw is the view's `visibleRect`, so the canvas's bar "0" would have shown in the snapshot before the fix.
   - **`live: true`:**
     - `ui.screenshot` takes `live` (bool, default false).
     - With `live`, VizDAW first calls `CGPreflightScreenCaptureAccess()`, which never prompts. If that is false, the answer is `failed` with "live screenshots need Screen Recording access for VizDAW (System Settings › Privacy & Security); omit `live` for the app-drawn picture". The app never calls `CGRequestScreenCaptureAccess`.
     - With access, it captures the `SCWindow` whose `windowID` is the window's `windowNumber` at `scale` (default the backing scale), and the answer has the same shape.
     - `vizctl screenshot --live` passes it.
   - Cost if wrong: the owner grants Screen Recording to use `live`; the default still shows clipping faults.
3. **Ruling (new projects, owner item 2).**
   - `Session::new_empty` and `Session::new_project` build their `Document` and then apply `SequenceCmd::New { name: "Sequence 1" }` through `core_model::command::apply`, before `Session::with`. So the project has no undo step and is not dirty, and Close asks nothing.
   - The sequence has no tracks, so the "+ Add Track" row and the Track menu are the first step.
   - `DocumentModel.apply` already selects the first top-level sequence. The window opens on Arrange, which is the default layout.
   - The "No Sequence" state:
     - title "No Sequence";
     - description "Add a sequence to arrange tracks in.";
     - a "New Sequence" button that runs `model.newSequence(.empty)`.
   - Tests that need a document with no sequence delete "Sequence 1" first (`transport_jumps.rs`'s `select a sequence first` block is one).
   - Cost if wrong: a one-line change to start with one track instead.
4. **Ruling (what a new track is, owner item 4).** `Session::new_track` makes one history step, labelled "New Audio Track", "New Instrument Track" or "New MIDI Track".
   - **Name:** "Track N", with the smallest N not taken in the sequence.
   - **Place:** below `after` when it names a track of the sequence, else at the end. The Swift side passes the selection's first track, then selects the new one.
   - **Each kind** is the existing commands in this order:
     - **Audio:**
       1. `LaneCmd::Add`;
       2. `LaneCmd::SetMonitor` with the Recording settings' new-track monitor, as `add_lane_monitored` does;
       3. `LaneCmd::SetInput` with `LaneInput::Audio { channels: InputChannels::Mono(0), return_of: None }` (the first input channel, 0-based);
       4. `LaneCmd::SetOutput` with the first output path in id order, or with one made by `RoutingCmd::AddOutput { name: "Audio 1", reference: "audio:1-2" }` (the values `TrackSynth` uses). Its strip feeds Master.
     - **Instrument:**
       1. `LaneCmd::Add`;
       2. `LaneCmd::SetDest` with the first destination in id order that `is_builtin_synth()`, or with one made by `RoutingCmd::AddDestination { name: "Built-in Synth", kind: MidiEndpoint { endpoint_ref: BUILTIN_SYNTH_REF, group: 0, channel: 0 }, default_patch: None }`;
       3. `LaneCmd::SetInput` with `LaneInput::Midi { port: None, channel: None }` (every source, the default MIDI input).
     - **MIDI:**
       1. `LaneCmd::Add`;
       2. `LaneCmd::SetDest` with the first destination in id order that `is_external()`. With none, there is no `SetDest`, and Swift's status line says "No external MIDI destination yet: choose one in the track's destination menu.";
       3. `LaneCmd::SetInput`, every source, as for Instrument.
   - **`RoutingCmd::AddOutput { name: String, reference: String }`** is the one new routing command. It wraps the existing `routing::add_output` and is labelled "Add Output". There is no other way to make an output path.
   - **`LaneCmd::Duplicate { seq, lane }`** is labelled "Duplicate Track".
     - It inserts a copy below the source, named "‹name› copy", with fresh lane, take and event ids.
     - It copies routing, input, monitor, flags, length, play quantize and shift, and the drum layout. `arm` is false.
     - Its body follows `clone_sequence`'s id reallocation for one lane.
   - **Delete Track** is the existing `LaneCmd::Remove`, relabelled "Delete Track". **Rename Track** is the existing `LaneCmd::Rename`.
   - Busy: `new_track` and `duplicate_track` refuse with `edit_open_busy()` while an edit is open, and through `records_busy` while recording, as other lane edits do.
   - Cost if wrong: a default changes in one function.
5. **Ruling (commands, keys and the menu, owner items 4 and 6).**
   - **The six registry entries**, menu "Track":

     | id | title | default key | params |
     |---|---|---|---|
     | `track.new_audio` | New Audio Track | ⌥⌘A | `seq`?, `after`? |
     | `track.new_instrument` | New Instrument Track | ⌥⌘S | `seq`?, `after`? |
     | `track.new_midi` | New MIDI Track | ⌥⌘X | `seq`?, `after`? |
     | `track.duplicate` | Duplicate Track | — | `seq`?, `lane`? |
     | `track.delete` | Delete Track | — | `seq`?, `lane`? |
     | `track.rename` | Rename Track | — | `seq`?, `lane`?, `name`? |

     - `seq` defaults to the selected sequence, and `lane` to the selection's first track.
     - The three new keys have `yields: true`.
     - Duplicate, Delete and Rename are registry commands too, so Settings › Keys can bind them and the channel can run them. No existing command is equivalent: `lane.*` has no add, duplicate, remove or rename.
     - `track.rename` without `name` over the channel is `invalid_params` "track.rename: `name` is required over the control channel". From the menu or a key it starts the header's inline rename field (`LaneHeaderView.beginRename`).
     - The params are integers ≥ 0 (`seq`, `after`, `lane`) and a string (`name`), checked by the existing `ParamSpec` checker.
   - **The menu.** `CommandMenu("Track")` sits after "Sequence", in the order of the table, with a divider after New MIDI Track. Each item uses `KeyMenu.shortcut(id)`. The New items are disabled with no selected sequence. Duplicate, Delete and Rename are also disabled with no selected track.
   - **The "+ Add Track" row.**
     - A mouse click pops up an `NSMenu` with the three New items.

The status line says "Add Track opens a menu: use track.new_audio, track.new_instrument or track.new_midi over the control channel." This is the precedent of `SynthSheets.trackSynthOnChannel`.

   - Cost if wrong: a key or a menu position moves.
6. **Ruling (the kind icon, owner item 5).**
   - `track_kind(doc, seq, lane) -> TrackKindRow` decides the kind; the first rule that matches wins:
     1. the input is `LaneInput::Audio` → Audio;
     2. `midi_dest` names a built-in synth or a `PluginInstrument` → Instrument;
     3. `midi_dest` names an external destination → MIDI;
     4. `audio_out` is set, or the active take has audio regions → Audio;
     5. otherwise → MIDI.
   - **Icons.** symbiotic-design 0.2.2 has no track-kind roles, so each kind uses an existing role:

   - The header's accessibility label gains the kind first: "Audio track, ‹name›, …".
   - Cost if wrong: one role swap in `AppIcon`.
