# VizDAW Tracks — The Usability Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the arrangement usable from a new project.
- The editor views stop painting over the track headers and the arrangement bar, and `ui.screenshot` stops hiding that kind of fault.
- New projects open on "Sequence 1".
- "Lane" reads "Track" everywhere a user sees it.
- A Track menu, a kind icon on each header, and Add Track in the Mix view.

**Architecture:**
- **`core-model`:**
  - `LaneCmd::Duplicate` is the one new command.
  - `LaneCmd::Rename` now refuses a blank name.
  - The existing `RoutingCmd::AddOutput` is reused.
  - No serialized type or file format changes.
- **`core-ffi`:**
  - `Session::new_track` and `Session::duplicate_track` live in `session.rs`, beside the private busy helpers.
  - `crates/core-ffi/src/tracks.rs` (new) holds the pure helpers: `TrackKindRow`, `track_kind` and the per-kind command lists.
  - `LaneRow` and the `state.get document` lanes JSON gain `kind`.
  - `new_empty` and `new_project` start with "Sequence 1".
  - `ControlRequest::Screenshot` gains `live`.
- **`core-control`:** six `track.*` commands (registry 157 → 163), `ui.screenshot`'s `live` parameter, and the Rust "Lane" scans.
- **`VizDAWEditors`:**
  - every NSView subclass clips to its bounds, and fields with focus rings sit inset inside their containers;
  - `WindowSnapshot` clips as AppKit does for views that do not clip;
  - the header shows the kind icon, and its "+ Add Track" row opens a menu.
- **`VizDAWAppModel`:** `TrackCommands`, `DocumentModel.newTrack` and `beginTrackRename`, the "Track" wording, and the clip and wording scans.
- **`VizDAW`:**
  - the Track menu;
  - the "No Sequence" state's New Sequence button;
  - Mix's Add Track;
  - the live screenshot, through ScreenCaptureKit.

**Tech Stack:** Rust 2024 (UniFFI 0.32.2); Swift 6 / SwiftPM (Swift Testing; SwiftUI and AppKit), macOS 14+; `symbiotic-design` 0.2.2 (unchanged pin); ScreenCaptureKit (system framework, autolinked); `sips` (system tool) in the e2e.

**Spec:** the owner's approval of 2026-11-05, items 1–6, recorded in Plan Rulings 1–8, and the clipping diagnosis summarised in Ruling 1. The diagnosis itself is in a session scratchpad and is not in the repo: Ruling 1 carries what it found. The pre-flight is `.superpowers/sdd/2026-11-05-tracks/preflight.md`, and its fold is in `fold-log.md` beside it.

Out of scope:
- renaming code identifiers, `lane.*` command ids, FFI names or file keys;
- reordering tracks by drag;
- track folders;
- the Linux app.

## Review Focus

These are the five failure modes a user is most likely to hit that the owner's scope implies but no feature test exercises, most likely first. Each is pinned by the named tests in its task.

1. **A view that still paints outside its frame, or a clipped focus ring.**
   - The cases:
     - the ruler's labels left of bar 1;
     - a header scrolled vertically past the add row;
     - the drum grid's, piano roll's and strip chart's canvases (`EditorCanvas` subclasses);
     - a transport field or list cell with the keyboard;
     - a view added later without `clipsToBounds`.
   - Expected:
     - nothing paints over a sibling;
     - every focus ring shows whole;
     - the scan fails on a new view that does not clip.
   - Pinned by `everyViewSubclassClipsToItsBounds`, `focusRingControlsHaveRoomInsideTheirClippingAncestors` and `theHeadersAndAddRowShowBesideTheCanvas` (Task 1), and the e2e's header pixel (Task 5).
2. **Old projects and scripts after the rename.**
   - The cases:
     - a project whose tracks are named "Lane 1";
     - a keys file that binds `lane.track_synth`;
     - `command.run lane.set_input`;
     - a `"lanes"` key in state answers;
     - a typed "lane" in a list cell's track column.
   - Expected: all of these work unchanged. Only text the app shows changes.
   - Pinned by `noLaneInWhatTheAppShows` (Task 3, which also asserts that the kept ids still parse), the existing `core-ffi/tests/format.rs`, and the e2e's `tracks_the_fake_synth` (Task 5).
3. **Creating a track in a thin document.**
   - The cases:
     - New Instrument Track with no built-in synth destination yet;
     - New Audio Track with no output path;
     - New MIDI Track with no external destination;
     - each of these with no sequence selected, while recording, or with an edit open.
   - Expected:
     - the synth destination or the output path is created inside the same undo step, and one Undo removes everything;
     - a MIDI track with no external destination is made with no destination, and the status line says so (Ruling 4);
     - with no sequence the items are disabled and the channel refuses with "Select a sequence first.";
     - while recording or with an edit open, the call is refused with Busy.
   - Pinned by `new_track_makes_each_kind_in_one_undo_step`, `a_midi_track_with_no_external_destination_has_none` and `new_track_refuses_unknown_ids_and_busy` (Task 2), and `trackItemsNeedASequence` (Task 4).
4. **New default keys taking a user's key.**
   - The case: a keys file that gives ⌥⌘A, ⌥⌘S or ⌥⌘X to another command.
   - Expected: the user's binding keeps the key, and the new command starts unbound there (`yields: true`, 7d controller ruling I3).
   - Pinned by `a_keys_file_key_wins_over_the_track_defaults` (Task 2) and `aSavedBindingKeepsItsKeyOverTheTrackDefaults` (Task 4).
5. **Duplicate, Delete and Rename on a busy track.**
   - The cases:
     - Duplicate a track with takes, a drum layout, audio regions and automation points;
     - Duplicate a Track Synth return track;
     - Delete the only track;
     - Delete or Duplicate while recording;
     - Rename to "" or "   " from the channel.
   - Expected:
     - per Ruling 4, Duplicate copies everything but automation points, with fresh ids and the copy's events indexed;
     - Duplicate refuses a return track and says why;
     - deleting the only track leaves an empty sequence with the "+ Add Track" row;
     - while recording: Busy, said in the status line;
     - a blank name is refused by the core.
   - Pinned by `duplicate_lane_copies_and_indexes_events`, `duplicate_lane_skips_automation_points`, `duplicate_lane_refuses_a_return_lane` and `rename_refuses_a_blank_name` (Task 2), and `deleteTheOnlyTrackLeavesTheAddRow` and `renameTrackGoesThroughTheHeader` (Task 4).

## Plan Rulings

Each ruling decides something the owner's scope leaves to the builder, as "what — why — cost if wrong". The owner's six items of 2026-11-05 bind. Rulings marked **(controller)** come from the pre-flight fold.

1. **Ruling (clipping, owner item 1).**
   - **What the diagnosis found** (the model is fine):
     - No view in `app/Sources` sets `clipsToBounds`, and the deployment target, macOS 14, defaults it to false.
     - `EditorCanvas`'s grid, content, overlay and ruler `CanvasLayerView`s fill their dirty rects and draw ruler marks from `dirty.minX - 60`. So bar "0" lands at a negative x, over the header column and the arrangement bar.
     - `ArrangementContainer` adds `headers`, then `canvas`, so the canvas paints on top of `LaneHeaderView`.
     - `WindowSnapshot.redraw` clipped each view to `visibleRect ∩ bounds`, so `ui.screenshot` hid the fault.
   - **What changes.** Every NSView subclass in `app/Sources` sets `clipsToBounds = true` on itself in each of its initializers, or inherits from a collected class that does. That includes `CanvasLayerView` in its own `init`.
   - **Focus rings (controller, I4): inset, so every container clips.**
     - Three controls draw their focus ring outside their own bounds and are the scan's only allow-list: `TransportTextField`, `ListCellField` and `HoldButtonView`. None of them may override `draw(_:)`.
     - Their containers clip like every other view, and leave room for the ring by insetting the control by `theme.spacing.xs`:
       - `TransportFieldsView` pins its stack `spacing.xs` inside its top, bottom and leading edges;
       - `ListEditorView`'s table sets `intercellSpacing` to `2 × spacing.xs` both ways, so each cell sits `spacing.xs` inside its `ListRowView`. List rows get taller by that inset.
       - `HoldButtonView`'s parent is a SwiftUI host, outside the scan, so nothing changes there.
     - README 233 checks the rings and the list's row height by eye.
   - Why: owner item 1 applied app-wide, with no container excused.
   - Cost if wrong: the list is a little less dense, and the inset becomes a token later.
2. **Ruling (`ui.screenshot`, owner item 1): the default stays app-drawn but clips as AppKit does for views that do not clip, and `live: true` is opt-in.**
   - **Why there is no live default:**
     - `CGWindowListCreateImage` is obsoleted in the macOS 15 SDK, which CI's Swift 6.1 builds against, so it does not compile there.
     - ScreenCaptureKit (`SCShareableContent`, `SCScreenshotManager.captureImage`, macOS 14) needs Screen Recording permission, even for the app's own windows.
     - A test must never prompt.
   - **The default, made faithful.** `WindowSnapshot.redraw` clips each view to `WindowSnapshot.clipRect(of:in:)`, the intersection in root coordinates of:
     - the root's bounds;
     - the view's own bounds when it clips;
     - each ancestor's bounds where that ancestor clips (`clipsToBounds`, or `NSClipView`).

     The redraw asks for the view's `visibleRect`. This models AppKit's behaviour for views that do not clip; it is not a window-server capture. The arrangement pixel test (Task 1) and the e2e pixel (Task 5) are the real checks.
   - **`live: true`.**
     - `ui.screenshot` takes `live` (bool, default false).
     - VizDAW first calls `CGPreflightScreenCaptureAccess()`, which never prompts. If it is false, the answer is `failed`: "live screenshots need Screen Recording access for VizDAW (System Settings › Privacy & Security); omit `live` for the app-drawn picture". The app never calls `CGRequestScreenCaptureAccess`.
     - With access, it looks up `SCShareableContent.excludingDesktopWindows(false, onScreenWindowsOnly: true)`. If no `SCWindow` has `windowID == UInt32(w.windowNumber)` (occluded, minimised or on another Space), the answer is `failed`: "the window is not on screen; live screenshots need it visible".
     - It captures at `scale` (default the backing scale) and answers in the same shape.
     - `vizctl screenshot --live` passes it.
     - A rebuilt app (`make-app.sh`, ad-hoc signed) loses an earlier grant, and README 233 says so.
   - Cost if wrong: the owner grants Screen Recording to use `live`; the default still shows clipping faults.

4. **Ruling (what a new track and a copy are, owner item 4).** `Session::new_track` makes one history step, labelled "New Audio Track", "New Instrument Track" or "New MIDI Track".
   - **Name (fix round 1):** "Audio N", "Inst N" or "MIDI N" by kind, with the smallest N not taken in the sequence, counted per prefix ("Inst", not "Instrument", so the name fits the header). `next_name` checks the result with `debug_assert!(valid_name(..).is_some())`.
   - **Place:** below `after` when it names a track of the sequence, else at the end. The Swift side passes the selection's first track, then selects the new one.
   - **Every kind** (controller ruling, final wave) first gets `LaneCmd::SetMonitor` with the Recording settings' new-track monitor, as `add_lane_monitored` did, right after `LaneCmd::Add`, so with the setting on Input a new instrument track plays the keyboard at once.
   - **Each kind** is then these existing commands, in order:
     - **Audio:**
       1. `LaneCmd::Add`;
       2. `LaneCmd::SetInput` with `LaneInput::Audio { channels: InputChannels::Mono(0), return_of: None }` (the first input channel, 0-based);
       3. `LaneCmd::SetOutput` with the first output path in id order, or with one made by the existing `RoutingCmd::AddOutput` (name "Audio 1", reference "audio:1-2", the values `TrackSynth` uses). Its strip feeds Master.
     - **Instrument:**
       1. `LaneCmd::Add`;
       2. `LaneCmd::SetDest` with the first destination in id order that `is_builtin_synth()`, or with one made by `RoutingCmd::AddDestination { name: "Built-in Synth", kind: MidiEndpoint { endpoint_ref: BUILTIN_SYNTH_REF, group: 0, channel: 0 }, default_patch: None }`;
       3. `LaneCmd::SetInput` with `LaneInput::Midi { port: None, channel: None }` (every source, the default MIDI input).
     - **MIDI:**
       1. `LaneCmd::Add`;
       2. `LaneCmd::SetDest` with the first destination in id order that `is_external()`. With none, there is no `SetDest`, and Swift's status line says "No external MIDI destination yet: choose one in the track's destination menu.";
       3. `LaneCmd::SetInput`, every source, as for Instrument.
   - **Busy (controller, M15).** `new_track` and `duplicate_track` take the session lock once and refuse with `edit_open_busy()` while an edit is open and with `records_busy` while recording. That is the pattern of the lane edits that retry inputs. Delete and Rename go through the existing edit path, which does not refuse while recording, so `TrackCommands` refuses those itself (M12).
   - **Duplicate Track (controller, I13): `LaneCmd::Duplicate { seq, lane }`, labelled "Duplicate Track".**
     - **What is copied.** It inserts a copy below the source, named "‹name› copy". The copy has the track's settings (routing, input, monitor, mute and solo, length, play quantize and shift, and the drum layout) and every take's events and regions, with fresh lane, take, event and drum-row ids. `arm` is false.
     - **Automation points are not copied.** `EventBody::Automation` events target strips, plugin params and destinations, not the track, so a copy would double the points on one target.
     - **The index.** It rebuilds the sequence through `put_sequence`, as `clone_sequence` does, so the copy's events are indexed. `Report.created` lists the new lane, take and event ids.
     - **Return tracks are refused.** On a Track Synth return track (`input` is `Audio { return_of: Some(_) }`) it refuses with `ModelError::invalid("Duplicate Track does not copy a Track Synth return track: duplicate its MIDI track and run Track Synth again.")`, and Swift shows that in the status line.
   - **Rename (controller, I12).** `LaneCmd::Rename` trims the name and refuses an empty result, or one with control characters, with `ModelError::invalid("a track name cannot be empty")` (or the existing name rule's text for control characters). **Delete Track** is the existing `LaneCmd::Remove`, renamed "Delete Track".
   - Cost if wrong: a default changes in one function.
