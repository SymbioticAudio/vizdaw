# Multi-Q in the EQ Slot Implementation Plan (6g)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** VizDAW ships Dusk Audio Multi-Q, built from a pinned source commit as CLAP and AU, inside `VizDAW.app`. New audio-track, instrument and built-in-synth strips get it in their EQ slot at its flat default, behind the Settings switch "Put an EQ on new channels". A Settings button, "Install Multi-Q for other apps", copies the AU to the user's Components folder. A DAWproject's built-in `Equalizer` device is imported onto Multi-Q's bands.

**Architecture:**
- **Build, outside the app.** `scripts/build-multiq.sh` clones the pinned commits into `target/multiq/`, builds only Multi-Q's CLAP and AU with CMake, and writes them to `target/multiq/out/` with the licence texts and a `SOURCE.txt`. CI caches `target/multiq/out`. VizDAW never downloads anything at run time.
- **Bundling.** `scripts/make-app.sh` copies both bundles into `VizDAW.app/Contents/PlugIns/` and the licences into `Contents/Resources/Licences/`. It signs each plug-in bundle, then the app.
- **`core-host::bundled`**:
  - `dir()` finds the app's `Contents/PlugIns`. `VIZDAW_BUNDLED_PLUGINS` overrides it, for `swift.sh` runs and tests.
  - `MULTIQ_CLAP_ID` and `MULTIQ_AU_ID` are the plug-in's identifiers.
  - `clap::search_paths()` puts `dir()` first. When two CLAP bundles have one ID, the catalog registers the bundled one.
- **`core-model`.** `History` gains `new_strip_eq: Option<PluginRef>`. When it is set, `History::execute` fills the EQ slot of each audio-path, instrument and built-in-synth strip the command created, in the same undo step. Buses and master are never filled. An import that loads its own EQ replaces the default, as `SetEq` already does.
- **`core-ffi::bundled`**:
  - the process-wide switch: `set_new_channel_eq` and `new_channel_eq`;
  - `multiq()`, which returns Multi-Q's `PluginRef` when the catalog has it and it is usable;
  - `history(doc)` and `arm(&mut History)`, which every session History goes through;
  - `install_multiq(dest, replace)`, the copy into Components, which tests point at a fake destination.
- **`core-io::dawproject`.** The reader turns `Equalizer` bands into `DpEqBand`s. The new `dawproject/multiq.rs` maps them onto Multi-Q's bands and parameters, and the import plan loads Multi-Q with those values through `SetPluginParams`.
- **Swift:**
  - `PluginSettings` (model) and `PluginSettingsView`, the new Settings › Plug-ins tab;
  - `PluginSettingsCommands`, which answers the control-channel commands `plugins.new_channel_eq` and `plugins.install_multiq`.

**Tech Stack:**
- Rust 2024: `core-host`, `core-model`, `core-io`, `core-ffi` with UniFFI 0.32.2, `core-control`, `vizctl`.
- Swift 6.1 / SwiftPM, tested with Swift Testing; macOS 14+.
- Build-time only: CMake (Homebrew `cmake` 4.x), Ninja and git.
- No new Rust crate.

**What we know about Multi-Q** (from `plugins/multi-q/CMakeLists.txt`, `EQBand.h` and `MultiQ.cpp` at the pin; Task 1 re-checks it):
- **Identifiers.**
  - CLAP ID `com.dusk-audio.multi-q`, with features `audio-effect equalizer mono stereo`.
  - AU `aufx/MulQ/Dusk`.
  - Product name `Multi-Q`, company `Dusk Audio`.
  - CMake targets `MultiQ_CLAP` and `MultiQ_AU`.
  - The root options `BUILD_MULTI_Q=ON` with every other `BUILD_*` set to `OFF`, plus `DUSK_COPY_AFTER_BUILD=OFF`, build Multi-Q alone.
- **Parameters.** CLAP parameter IDs are `(u32) juce::String(id).hashCode()`, where `hashCode` is `h = h*31 + c` over the UTF-32 characters with wrapping arithmetic. For example, `band1_freq` is 1472467003.
- **Bands.** There are 8 bands, N = 1…8. Every band has `bandN_enabled`, `bandN_freq` (20–20000 Hz, log) and `bandN_q` (0.1–100, log, default 0.71).

  | Band | Role | Default frequency | Default enabled | `bandN_gain` (−24…+24 dB, default 0) | `bandN_shape` | `bandN_slope` |
  |---|---|---|---|---|---|---|
  | 1 | High-pass | 20 Hz | off | no | none (fixed type) | {6, 12, 18, 24, 36, 48, 72, 96} dB/oct, default 12 |
  | 2 | Low shelf | 100 Hz | on | yes | {Low Shelf, Peaking, High Pass} | no |
  | 3–6 | Parametric | 200, 500, 1000 and 2000 Hz | on | yes | {Peaking, Notch, Band Pass, Tilt Shelf} | no |
  | 7 | High shelf | 4000 Hz | on | yes | {High Shelf, Peaking, Low Pass} | no |
  | 8 | Low-pass | 20000 Hz | off | no | none (fixed type) | as band 1 |
- **State.** The plug-in saves its state as APVTS XML. VizDAW never parses it: it stays an opaque blob.

## Owner Decisions

These are needed before execution. The controller asks them at the start, and Task 1 Step 1 checks they are answered.

- **Owner answer, 2026-11-13: D1 (a)** — accept the AGPLv3 duties and ship JUCE Multi-Q (Branch A).
- **D1 — AGPL through JUCE (licence finding; it blocks shipping until the owner rules).** Multi-Q's GPL-3.0 code is linked with JUCE 8.0.4, which VizDAW can only take under AGPLv3, since it holds no commercial JUCE licence. GPLv3 §13 permits combining GPLv3 and AGPLv3 work, and VizDAW conveys the plug-in as a separate bundle. The AGPL's network clause concerns users interacting over a network, which a local plug-in is not. **So the combination is permitted, but it carries duties:**
  - the app ships the AGPLv3 text;
  - the app ships a written offer of the corresponding source: Multi-Q, JUCE and clap-juce-extensions at their pins;
  - VizDAW stops describing the whole `.app` as plain GPL-3.0-only.

  **Choices:**
  - **(a)** Accept these duties and ship the JUCE Multi-Q. This is the plan's default branch, A.
  - **(b)** Refuse AGPL code in the app. Then branch A fails, and so does the spec's fallback (branch B below), because ZL Equalizer 2 is itself AGPL-3.0 on an AGPL JUCE 9 fork. Execution stops and goes back to the owner. The option that avoids AGPL is **Multi-Q 2**, the repo's own ISC-framework build (`plugins/multi-q/daf-plugin`, CLAP ID `com.duskaudio.multiq2`, GPL-3.0-or-later, no release tag yet). It would need its own small plan revision.
- **D2 — Pin (owner, 2026-11-13): the `multi-q-v0.10.9` release tag**, commit `00e3dc10f4a26931da823eca425dc9860d5e1737`. The licence check runs on that commit.

## Review Focus

These are the five failure modes a user is most likely to hit, most likely first. Each is pinned by named tests in its task.

1. **Multi-Q is missing, off or broken when a track is made.**
   - Examples:
     - the first launch, before the scan has seen the bundled plug-in;
     - Multi-Q disabled in the Plugin Manager;
     - Multi-Q blocklisted after a crash;
     - a build without Multi-Q (a fork, Linux);
     - the switch turned off.
   - Expected:
     - the new strip shows "EQ ＋", exactly as before 6g;
     - nothing is listed or alerted;
     - no placeholder slot is made.
   - Pinned by Task 3's `no_default_when_multiq_is_unusable` and `switch_off_leaves_the_slot_empty`.
2. **One undo step, and only new channels.**
   - Examples:
     - New Audio Track, then Undo;
     - Redo after the switch was turned off;
     - Duplicate Track (it adds no strip, so it adds no EQ);
     - Add Bus;
     - a DAWproject merge that adds one strip and changes another;
     - the template "Same lanes as".
   - Expected:
     - the strip and its EQ come and go together (a strip exists once per output path or built-in synth, so only the first audio track and the first synth track of a project make one);
     - redo replays exactly what was done;
     - buses, master and strips that already existed are never filled or emptied.
   - Pinned by Task 3's `the_fill_is_part_of_the_same_step`, `only_new_audio_instrument_and_synth_strips`, `second_tracks_add_no_strip` and `new_track_reads_the_switch`, and Task 5's `merge_fills_only_new_strips`.
3. **Two copies of Multi-Q.**
   - Example: the user also has a Multi-Q CLAP (older or newer) in `~/Library/Audio/Plug-Ins/CLAP`, so the catalog has two bundles with one ID.
   - Expected: projects load the bundled copy, and "Install for other apps" leaves the user's CLAP alone.
   - Pinned by Task 2's `bundled_copy_wins_a_shared_id`.
4. **Installing for other apps when something is already there.**
   - Examples:
     - an existing `Multi-Q.component`;
     - a symlink or a plain file at that name;
     - a missing `Components` folder;
     - a read-only destination;
     - a full disk mid-copy;
     - the bundled AU missing from a dev build.
   - Expected:
     - existing files are replaced only after "Replace" (or `replace: true`);
     - a symlink is refused;
     - a failed copy leaves no half bundle and no staging folder;
     - each failure is one sentence.
   - Pinned by Task 4's `install_*` tests.
5. **Another DAW's `Equalizer` in shapes Multi-Q cannot hold.**
   - Examples:
     - nine bells;
     - two high-passes;
     - a band at 5 Hz or 40 kHz;
     - +30 dB of gain;
     - Q 0 or NaN;
     - `unit="normalized"` with no `min`/`max`;
     - a band with no `Freq`;
     - `order="3"` on a high-pass;
     - a disabled device;
     - two `Equalizer`s on one channel.
   - Expected:
     - every band that fits plays as written (clamped values get a Changed line);
     - bands that do not fit are Left out with their settings;
     - a disabled device arrives bypassed;
     - nothing panics.
   - Pinned by Task 5's `bands_map_by_type`, `values_are_clamped_and_listed` and `unmappable_bands_are_left_out`.

## Plan Rulings

These are this plan's decisions where the spec leaves a choice. Each names its cost if wrong.

1. **Which EQ is shipped, and the fallback decision rule.**
   - **Branch A, the default.** Ship Multi-Q (JUCE build) at the pins above, provided the owner chose D1 (a).
   - **Branch B, the spec's fallback.** Switch to ZL Equalizer 2 when any one of these holds:
     - **(i)** Task 1's licence check finds that the pinned Multi-Q is not wholly GPL-3.0-compatible: a `LICENSE` other than GPLv3, or a source file Multi-Q compiles that carries an incompatible licence;
     - **(ii)** `scripts/build-multiq.sh` cannot build `MultiQ_CLAP` and `MultiQ_AU` at the pins on macOS 14+ arm64, after one honest fix attempt limited to CMake flags;
     - **(iii)** the built CLAP fails `bundled_multiq_lists_and_loads` or `bundled_multiq_is_flat_by_default`.

     Branch B pins:
     - ZL Equalizer at `ZL-Audio/ZLEqualizer` `0f686a2d80a7d6a0a7ead35d740defa534cb70ca` (AGPL-3.0, its JUCE fork AGPLv3);
     - clap-juce-extensions at `e8de9e8571626633b8541a54c2406fccc4272767`, added by the script with `add_subdirectory` and `clap_juce_extensions_plugin(TARGET … CLAP_ID "com.zl-audio.equalizer" …)`.

     Branch B is allowed only under D1 (a), because it is AGPL itself. The constants `BUNDLED_EQ_CLAP_ID`, the AU ID, the band table (Task 5) and the copy text change with it.
   - **Branch C, stop.** If D1 is (b), or Branch B also fails (i)–(iii), stop and report to the owner, naming Multi-Q 2 as the candidate. Do not improvise a third EQ.
   - **Reporting.** Task 1's report and Task 6's final report state which branch shipped. Settings › Plug-ins shows the shipped EQ's name.
   - **Cost if wrong:** a week lost on a build that cannot ship. The rule keeps the switch mechanical.
2. **Where the bundles live.**
   - Both bundles go in `Contents/PlugIns/`: `Multi-Q.clap` and `Multi-Q.component`.
   - The CLAP search finds only `.clap` there. macOS does not register a v2 AU inside an app, so the AU is only a payload for "Install for other apps". VizDAW itself always uses the CLAP.
   - The licence texts and `SOURCE.txt` go in `Contents/Resources/Licences/Multi-Q/`.
   - **Cost if wrong:** a notarisation complaint about code in `Resources`, which this layout avoids.
3. **`core-host::bundled::dir()`** returns, in order:
   - `VIZDAW_BUNDLED_PLUGINS` when it is set, not empty and an existing folder;
   - else `<exe>/../../PlugIns`, when the running executable sits in `<X>.app/Contents/MacOS/` and that folder exists;
   - else `None`.

   `vizdaw-scan` lives in `Contents/MacOS` too, so it resolves the same folder. `scripts/swift.sh` exports `VIZDAW_BUNDLED_PLUGINS="${VIZDAW_BUNDLED_PLUGINS:-$root/target/multiq/out}"`, so dev runs see Multi-Q once it is built.
4. **Search order and duplicates.**
   - `clap::search_paths()` is `[bundled dir] + the standard folders`.
   - `Catalog::apply_to` registers a CLAP path for an ID from the entry under `bundled::dir()` when one exists, and otherwise from the first entry. Before 6g the last entry won.
   - Status and the user's on/off stay keyed by ID, as before.
5. **Which strips get the default.**
   - Only `StripKind::AudioPath`, `StripKind::Instrument` and `StripKind::BuiltinSynth` strips that appear in the command's `Report.created`, and only while their `eq` is `None` after the command.
   - Never `Bus`, `Master` or `InstrumentOutput`. An extra output of a multi-output instrument is not a "new channel" in the spec's list.
   - The slot is `PluginSlot::new(<a new instance ID from the document's counter>, multiq_ref)`, with no state and no overlay, which is the plug-in's flat default. Its `PluginInstanceId` is pushed onto `Report.created`.
   - **Cost if wrong:** EQs appearing on buses. The test lists every kind.
6. **The fill lives in `History::execute`, not in each command.**
   - The value is a `History` field, so every route goes through it in the same undo step: commands, templates, imports applied into the session's History, merges. `core-model` stays pure.
   - `core-io` never sets the field: its scratch Histories (for example `merge/decide.rs`'s view of "theirs") must not invent EQs.
   - `core-ffi` builds every session History with `bundled::history(doc)`, which replaces the `History::new` calls at `session.rs` 328, 4686/4688, 4915/4939 and 5023/5028 (not the bounce copy at 10742 or the unit test at `templates.rs` 195). It calls `bundled::arm(&mut inner.history)` under the session lock in every Session method that builds strips (Task 3 Step 7 lists them, including `new_track`), so a change of the switch or the catalog applies to the next command.
7. **When Multi-Q counts as usable.** `bundled::multiq()` returns the catalog's `PluginRef` for `(Clap, MULTIQ_CLAP_ID)` only when:
   - its status is `Ok` or `NotValidated`;
   - the user has not disabled it;
   - its path is under `bundled::dir()`, or no bundled dir exists (a user-installed copy still counts then).

   Otherwise it returns `None`. Nothing is loaded to decide this.
8. **The switch.**
   - "Put an EQ on new channels" is a machine preference, never in a project: key `VizDAW.newChannelEq` in `UserDefaults`, default `true`.
   - The app pushes it to the core at launch and on every change, as the automation settings do. `core-ffi` keeps it in a `static AtomicBool`, default `true`.
9. **Install for other apps.**
   - The source is `bundled::dir()/Multi-Q.component`. The destination folder is `dest`, or `$HOME/Library/Audio/Plug-Ins/Components` when `dest` is `None`.
   - Steps:
     1. lstat the target `Multi-Q.component`. A symlink is refused. An existing file or folder without `replace` returns `VizError::Exists`.
     2. Create the folder (`create_dir_all`).
     3. Copy the bundle recursively into `.Multi-Q.component.vizdaw-partial-<pid>`, refusing symlinks inside the source.
     4. With `replace`, move the old bundle to `.Multi-Q.component.vizdaw-old-<pid>`.
     5. Rename the staged bundle into place, then remove the old one.
     6. On any failure, remove the staging folder and restore the old bundle.
   - It returns the installed path. It never runs `auval` or anything that registers the component; the system picks it up by itself.
   - **The sentences:**
     - "Multi-Q is not in this build of VizDAW." (no bundled AU);
     - "Something that is not Multi-Q is in the way: <path>." (a symlink, or a plain file without `replace`);
     - "Multi-Q could not be installed: <io error>."
10. **The `Equalizer` mapping.**
    - **When it applies.** Only when `ImportEnv.eq_plugin` is `Some`, meaning Multi-Q is usable here. The switch does not matter, since this is the import's own EQ. When it is `None`, 6d's behaviour stands: Left out, with the settings listed.
    - **Which slot.** The device loop first finds whether the channel has an EQ-tagged plug-in; if so, that plug-in takes the EQ slot whatever the device order and every `Equalizer` becomes a Multi-Q insert. Otherwise the first `Equalizer` takes the slot and each later one becomes a Multi-Q insert at its position.
    - **Armed imports.** With the History armed (Task 3), a new strip first gets the flat default and the import's `SetEq` replaces it. A strip with no EQ in the file keeps the flat default, also when the file is a VizDAW export whose user had removed the EQ (spec §8: imports are filled unless the import fills the slot).
    - **The device's own `Enabled` false** makes the slot bypassed.
    - **Band assignment.** Bands are taken in two passes over their file order:
      - first, the bands with few candidate slots: `highPass`, `lowPass`, `lowShelf` and `highShelf`;
      - then `bell`, `notch` and `bandPass`, sorted by frequency.

      Each takes its first free candidate:

      | DAWproject `type` | Candidates (Multi-Q band: shape) |
      |---|---|
      | `highPass` | 1; 2: High Pass |
      | `lowPass` | 8; 7: Low Pass |
      | `lowShelf` | 2: Low Shelf |
      | `highShelf` | 7: High Shelf |
      | `bell` | 3, 4, 5, 6: Peaking; 2: Peaking; 7: Peaking |
      | `notch` | 3, 4, 5, 6: Notch |
      | `bandPass` | 3, 4, 5, 6: Band Pass |

    - **Unused bands.** Every Multi-Q band no file band took gets `bandN_enabled = 0`. This makes the result exactly the file's EQ: Multi-Q's defaults are flat anyway, so this only removes stray shelves for reading clarity.
    - **Values.**
      - **Frequency.** `Freq` in `hertz`, or in `normalized` with a finite `min` < `max` (scaled), is clamped to 20–20000 Hz. Any other unit Leaves the band out.
      - **Gain.** `Gain` in `decibel` (or `linear`, converted to dB) is clamped to ±24 dB and ignored for bands 1 and 8.
      - **Q.** `Q` in `linear` (the XSD's usual unit for it) is clamped to 0.1–100. A missing value keeps the default.
      - **Slope.** `order` n on bands 1 and 8 becomes the slope nearest to 6·n dB/oct. On band 2 or 7 used as a pass filter, an `order` other than 2 gets a Changed line "slope kept at 12 dB/oct".
      - **Enabled.** `Enabled` false sets `bandN_enabled = 0`.
      - **Lines.** Each clamp gets a Changed line naming the track and the band. Non-finite values Leave the band out.
    - **Not mapped.** `InputGain` and `OutputGain` are Left out, with their values listed.
    - **How values are written.** The overlay goes through `MixerCmd::SetPluginParams` in the plug-in's CLAP value domain, as Task 1's dumped table records it: plain, or normalised with the range's formula. That keeps the mapping pure and the plug-in unloaded.
    - **Cost if wrong:** a curve that differs from the file. Task 5's render check measures it.
11. **The export does not change.** A Multi-Q EQ is written as the `ClapPlugin` 6d writes today, with its state and its EQ tag, so a VizDAW → DAWproject → VizDAW trip restores it byte-equal. The mapping applies only to the `Equalizer` element.
