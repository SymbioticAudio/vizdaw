# VizDAW 5f-4 — Kontrol S-Series MK3 (DAW mode and plug-in pages) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Kontrol S-Series MK3 keyboard (S49, S61, S88; firmware 2.0 or later) drives VizDAW over its "DAW" MIDI port as a fourth surface kind. Its transport buttons run the transport; its eight knobs, track buttons and 4-D encoder ride and switch an 8-track bank of the mixer, with track and bank navigation; its screen shows each track's name, type, colour, volume and pan text, mute, solo, arm, selection and meters, and the tempo. In Plug-in mode it shows VizDAW's own parameter pages for any plug-in on the selected track (the chain, eight parameter names and values per page, the page, the preset name), its knobs move those parameters, and its preset buttons step the plug-in's own presets. Its "Main" port stays an ordinary keyboard for the lanes.

**Architecture:**
- **`core-surface::kontrol`** is a new pure module: the wire codec (the NI SysEx frame, display text, tempo, relative values, port matching, meter scale, track types and colours) and the `Kontrol` state machine behind the existing `Surface` trait (handshake, input, feedback with a send-only-what-changed cache, goodbye). It runs and is tested on Linux.
- **The shared types grow by what the Kontrol shows and asks:** `TrackKind` and `StripView.kind`; `MixerView.tempo`, `.soloing` and `.page` (a `PluginPageView`); `SurfaceAction::PluginSlot`, `PluginPage` and `Preset`; trait defaults `shows_page`, `goodbye` and `take_problem`.
- **`core-ffi::surfaces`** adds the kind (`SurfaceKindRow::KontrolMk3`, its own bank of 8, position 0), goodbye on removal and on `shutdown`, the unit's problem lines, its meters counted, the plug-in page when a Kontrol in Plug-in mode is due, and `kontrol_ports()` (the ports whose names say KONTROL, MK3 and DAW).
- **`Session`** fills the new view fields, keeps each document's page focus (which plug-in of the selected strip's chain and which page), and applies the three new actions. A preset step goes through two new `PluginInstance` methods: `presets` and `load_preset`. AU implements them with its factory presets. CLAP keeps the defaults (none).
- **The app:** Settings › Surfaces offers "Kontrol S-Series MK3 (DAW mode)", picks the DAW port by itself, and shows the trademark notice. The channel's `surface.add` takes `type: "kontrol_mk3"`. Also an e2e, README 189–198 and backlog rows.

**Tech Stack:** Rust 2024 (`core-surface`, `core-ffi` with UniFFI 0.32.2, `core-host`, `platform-macos`, `core-control`, `vizctl`), Swift 6 / SwiftPM (Swift Testing), macOS 14+.

**Spec:** `docs/superpowers/specs/2026-10-18-recording-audio-design.md`. The writer's commit adds §8.4 "Komplete Kontrol MK3" and the §13 row "5f-4". This plan delivers §8.4, the `surface.add` type of §12.1, the §12.2 rule for this surface (a malformed or unknown message is ignored and counted), and the §12.3 tests below. Read §8 whole and the 5f-1 plan's Rulings 2–5, 9–13 and 17 (`docs/superpowers/plans/2026-11-02-control-surfaces.md`). This plan builds on them unchanged.

**Research:** `.superpowers/kontrol-mk3-research.md` (not committed) has the protocol facts with their sources. The byte tables below are the plan's binding copy; where the research marks a fact uncertain, the plan rules a value and README 198 asks the owner to check it on the hardware.

- **Protocol values used verbatim (the byte tables of Rulings 4, 5, 6 and 8):**
  - The SysEx header is `F0 00 21 09 00 00 44 43 01 00`. A message is `header, cmd, value, index, info…, F7`.
  - All CCs are on MIDI channel 16 (status `BF`).

  - The VU is "value 2, index 0, info = 16 bytes (L/R for 8 tracks, 0–127)".
  - The colour is `"#RRGGBB"` text.

## Review Focus

These are the five failure modes a user is most likely to hit, most likely first. The spec implies them but does not spell them out. Each is pinned by named tests in its task.

1. **The keyboard that never comes online.** The DAW port is picked wrong (the "Main" or "MIDI 2.0" port), the keyboard runs old firmware and answers version 3, it is switched on after VizDAW, or it leaves DAW mode and comes back.
   - Expected:
     - Settings picks the port whose name has KONTROL, MK3 and DAW.
     - A version below 4 shows a problem line naming the version and "firmware 2.0", and the unit stays "Connected · not answering".
     - The hello is repeated every 2 s until an answer comes.
     - A keyboard goodbye releases what it held, and a later answer brings it back with its name and a full refresh.
   - Pinned by `daw_ports_are_found_by_kontrol_mk3_and_daw` (Task 1), `a_wrong_version_is_a_problem_and_keeps_it_offline`, `hello_is_repeated_every_2_s_until_answered` and `the_keyboards_goodbye_takes_it_offline_until_it_answers_again` (Task 1), `a_wrong_protocol_version_is_named_in_the_problems` and `kontrol_ports_lists_only_daw_ports` (Task 1), `a_goodbye_from_the_keyboard_releases_its_knobs` (Task 2), and `aKontrolDraftPicksTheKeyboardsDawPorts` / `aKontrolDraftWithoutAKeyboardSaysSo` (Task 6).
2. **Keys leaking out, or knobs leaking in.** The lane is armed on All MIDI Inputs and the user plays the keys and turns the knobs.
   - Expected: the keys (Main port) record and play thru as before. Nothing from the DAW port reaches a lane: no knob CC, no transport CC, no SysEx.
   - Pinned by `the_daw_port_is_the_surfaces_and_the_main_port_the_lanes` (Task 1).
3. **A knob ride that never ends or ends twice.** A volume knob is turned and let go. While it is held, the USB cable is pulled, the surface is removed, the window loses focus, or the keyboard says goodbye.
   - Expected: the ride is one "Set Fader" step, released 500 ms after the last turn and stamped at the last value. Every way of losing the unit releases it exactly once.
   - Pinned by `volume_and_pan_knobs_ride_the_shown_strips_and_release_after_idle`, `a_goodbye_from_the_keyboard_releases_its_knobs` and `release_all_and_release_holds_answer_the_knobs_it_holds` (Task 2), and `a_volume_knob_ride_is_one_set_fader_step` (Task 4). The 5f-1 tests of the shared paths still run.
4. **The screen showing the wrong thing.** The user banks past the last strip, selects off-screen, solos a track in another bank, or changes the selection while in Plug-in mode.
   - Expected:
     - Slots past the last strip are empty.
     - Track navigation moves the Kontrol's own bank to the selection, and the MCU group's bank does not move.
     - Muted-by-solo lights for every unsoloed track when any track is soloed.
     - The navigation lights say where one can go.
     - Changing the selected strip starts its plug-in view at the chain's first plug-in, page 1.
   - Pinned by `track_navigation_selects_the_next_strip_and_the_bank_follows` (Task 2), `a_bank_shows_the_next_eight_strips`, `the_navigation_lights_say_where_one_can_go` and `mute_solo_arm_select_and_muted_by_solo_light` (Task 3), and `track_navigation_moves_the_kontrols_own_bank_with_the_selection`, `the_kontrol_sees_kinds_colours_tempo_and_solo` and `the_plugin_page_starts_over_when_the_selection_changes` (Task 4).
5. **A flood or a stall.** The keyboard gets every message again every 20 ms, or a long or non-ASCII track name, a fast meter, or garbage from the port stalls it.
   - Expected:
     - Only what changed is sent.
     - Text is printable ASCII and at most 32 bytes.
     - Meters go as one 16-byte message, are counted rather than logged, and are not resent while unchanged.
     - Garbage is counted and never panics.
   - Pinned by `only_what_changed_is_sent_again`, `volume_and_pan_read_as_text` and `meters_are_one_message_of_sixteen_levels` (Task 3), `display_text_is_printable_ascii_and_at_most_32_bytes` (Task 1), `kontrol_meters_are_counted_not_listed` (Task 4) and `hostile_kontrol_bytes_are_ignored_and_counted` (Task 2).

     - The plan runs after 5f-3 and before 5g-1.
   - **Why:**
     - Phase 2 reuses phase 1's state machine, cache and registry wiring.
     - Phase 1 alone is about 4 tasks, so two plans would duplicate the header and the final review.
   - **Cost if wrong:** one larger final review.
2. **Ruling (the kind and its bank).**
   - **What:**
     - `SurfaceKind::KontrolMk3` (serde `"kontrol_mk3"`, `SurfaceKindRow::KontrolMk3`, channel `type: "kontrol_mk3"`) is configured on the keyboard's DAW port for input and output.
     - Each Kontrol is a bank group of its own (`Group::Kontrol(SurfaceId)`): 8 strips from its own offset, as a HUI is. Its position must be 0 (refused otherwise: "a Kontrol S-Series MK3 keyboard is a bank of its own: `position` must be 0").
     - It counts toward the 16 surfaces. Several Kontrols are allowed.
     - The Main port is never configured, so the 5f-1 claims leave it to the lanes (owner).
   - **Why:**
     - The keyboard shows 8 tracks and has its own bank buttons.
     - Joining the MCU group would move the MCU's faders whenever the keyboard banks.
   - **Cost if wrong:** a group change in `Unit::group`.
3. **Ruling (finding the port; owner: "match robustly").**
   - **What:**
     - `kontrol::is_daw_port(name)` splits the name, upper-cased, at every character that is not a letter or digit. It is true when the words include `KONTROL`, `MK3` and `DAW`.
     - That matches `KONTROL S88 MK3 DAW` and `Native Instruments - KONTROL S61 MK3 - DAW`. It does not match `… Main`, `… MIDI 2.0`, the MK2's `Komplete Kontrol DAW - 1` or the Windows/Linux names.
     - `kontrol_ports()` answers the transport's sources and destinations that match, in the transport's order.
     - Settings fills both pickers with the first match when the type becomes the Kontrol, and the user can pick any port by hand.
   - **Why:**
     - The research shows two macOS spellings, endpoint versus "manufacturer - device - entity".
     - The owner confirms the names in alpha testing (README 189 asks for them).
   - **Cost if wrong:** one function and its test, or a hand pick.
4. **Ruling (handshake, identity, goodbye).**
   - **What:**
     - `hello()` is `BF 01 04` (protocol version 4).
     - The keyboard's answer `BF 01 v` puts the unit online when `v ≥ 4` (it speaks 4).
     - When `v < 4` the unit stays offline. Once per answer it reports the problem "the keyboard answered protocol version {v}; VizDAW needs version 4 (keyboard firmware 2.0 or later)". The registry prefixes it with "surface {id}: " and adds it to `state.get surfaces` problems.
     - Until an answer of 4 or more, every other message is ignored and counted, and feedback sends nothing except the hello again `HELLO_EVERY` = 2 s after the last one.
     - After an accepted answer the next feedback starts with IDENTITY `sysex(0x07, 1, 0, b"Generic")` (DAW version 1.0, name "Generic"), followed by the full state. A refresh (bank change, reconnect) resends the state but not the identity.
     - The keyboard's `BF 02 xx` takes the unit offline. It answers the releases of what the unit held, through the shared `Unit::set_online`, and the hello repeats until an answer.
     - `goodbye()` is TRACK_AVAILABLE 0 for slots 0–7, then `BF 02 00`; afterwards the unit is offline. It is sent when the surface is removed and, through `surfaces::goodbye_all()` called from `shutdown()`, when the app quits.
     - Closing the focused document blanks the unit as 5f-1 does: an empty view, so every slot reads empty.
   - **Why:**
     - DrivenByMoss flushes state only after the version reply.
     - The identity name picks the plug-in view's background. An unknown name reportedly gives an unreadable one.
     - Sending another DAW's name would misrepresent VizDAW. "Generic" names no product and is the neutral choice DrivenByMoss offers.
   - **Cost if wrong:** the background is unreadable. That is one constant (`IDENTITY_NAME`), and README 198 checks it; "VizDAW" is the fallback.
5. **Ruling (what the controls do).**
   - **What:** The keyboard sends these, on channel 16 unless they are SysEx.
     - **Transport** (act on a value above 0; a 0 is a release and does nothing):
       - `10` Play → `Command("transport.play")`, which only starts (owner);
       - `11` Restart → `Command("transport.return_to_start")`, then `Command("transport.play")`;
       - `12` Record → `transport.record`; `14` Stop → `transport.stop`; `16` Loop → `transport.loop`;
       - `20` Undo → `edit.undo`; `21` Redo → `edit.redo`.
       - Count-in `13`, Clear `15`, Metro `17`, Tap Tempo `18`, Quantize `22`, Automation `23`, Shift `04`, clip and scene navigation `32`/`33` and Move Loop `35` do nothing and are **not** counted. VizDAW has no metronome, and its quantize opens a sheet.
       - The keyboard has no Rewind or Fast Forward. Move Transport `34` (relative) is `Jog(n)`, a sixteenth note per step in the app (5f-1 Ruling 12).
     - **Knobs:**
       - Volume `50+k` and Pan `58+k` (k = 0–7, relative) move the fader or pan of the strip shown in slot k through `IdleTouches`: touched by the first value, released 500 ms after the last (5f-1 Ruling 2).
       - Each step moves the target by `KNOB_STEP` = 0.005 of its range, so 200 steps cover the travel.
       - A relative value of 0 or 64 is no movement and is not counted.
     - **Selected track:**
       - The 4-D encoder's `64` (volume) and `65` (pan) are relative moves of the selected strip, the first of the shown strips whose `select` is set.
       - `66`/`67` press mute or solo on it, as clicks at the toggled value.
       - With no selected strip among the shown ones, all four are ignored and counted.
     - **Track buttons (SysEx):** `42` select → `Select(strip)`; `43` mute and `44` solo → clicks at the toggled value; `45` arm → `Arm(strip)`. The *index* is the slot. A slot past 7 or an empty slot is ignored and counted.
     - **Navigation:**
       - `30` tracks (relative sign: 1–63 next, 65–127 previous) selects the next or previous strip in display order, starting from the selected one; with none selected, the first shown. When the new strip is outside the shown 8, `Channel(±d)` moves the bank just enough to show it. At either end nothing happens, uncounted.
       - `31` banks is `Bank(±1)` in Mixer mode and `PluginPage(±1)` in Plug-in mode.
       - `36` presets is `Preset(±1)` in either mode.
     - **Mode:** `05` with value 0 is Mixer, 1 is Plug-in. Other values are ignored and counted. The mode is echoed back in feedback.
     - **Plug-in (SysEx and CC):**
       - Parameter knobs `70+k` (relative) move parameter k of the shown page through `IdleTouches`, in Plug-in mode only (in Mixer mode they are ignored and counted). A knob with no parameter is ignored and counted.
       - SysEx `70` (the soft buttons, index = chain slot) → `PluginSlot(index)`; a slot past the shown chain is ignored and counted.
       - SysEx `74` (index = page) → `PluginPage(index − shown page)`. The page shown already is nothing, uncounted; a page past the count is ignored and counted.
     - **Heard but unused:** SysEx `19` (the keyboard's tempo) changes nothing and is not counted. The keyboard's tempo is shown, never sent back: it is display-only.
     - **Ignored and counted:** any other CC on channel 16, any message on another channel (including notes), SysEx with another header, a cut frame, an unknown command, and `7F` (high-resolution deltas, which VizDAW never asks for).
   - **Why:**
     - These are DrivenByMoss's mappings, mapped onto VizDAW's existing registry commands and the 5f-1 gesture rules.
     - Not counting buttons that have no counterpart keeps `ignored` a fault counter.
     - The keyboard's tempo stays display-only, because a tempo edit from a keyboard is an undo step the owner did not ask for.
   - **Cost if wrong:** one table entry each. `KNOB_STEP` and the tempo rule are README 198 checks with backlog rows.
6. **Ruling (VizDAW's own plug-in pages; owner: "VizDAW's own parameter pages for any plug-in").**
   - **What:**
     - The **chain** of a strip is its plug-in instrument, when the strip is `Instrument(d)` or `InstrumentOutput(d, _)` and `d` is a plug-in instrument, followed by its inserts in processing order. Names are `PluginRef.name`.
     - Each document keeps a **page focus** (`SessionSurfaces.page: PageFocus { strip, slot, page }`). Whenever the first selected strip differs from `focus.strip`, the focus becomes that strip, slot 0, page 0.
     - The **pages** of the focused plug-in are its automatable, non-hidden parameters in the plug-in's list order (the MCU's filter), cut into pages of 8. `pages = max(1, ceil(n / 8))`; the page name is `"Page {page + 1}"`. Values and their text are the MCU's: the heard value, and `format!("{plain:.2}")`.
     - `PluginSlot(i)` sets slot i, page 0. `PluginPage(n)` moves the page by n, and does nothing (uncounted) past either end.
     - With no selected strip, an empty chain, or a plug-in that is not running, `PluginSlot` and `PluginPage` are refused and counted. The view's page is then `None`, and the keyboard shows an empty chain.
     - The page is computed only when a due Kontrol is in Plug-in mode (`Due.page`).
   - **Why:**
     - The owner wants any plug-in to work.
     - The list order is what the plug-in's own generic view shows. Pages the user arranges are a later refinement (backlog).
   - **Cost if wrong:** the page builder (`slot_param_views`) and its test.
7. **Ruling (presets; owner: "preset previous/next").**

   - **Per slot k (0–7), showing strip `first + k`:**
     - `40` available: value = the track type. `Instrument` → 2 (MIDI), `Audio` → 3, `Bus` → 5 (return), `Master` → 6, an empty slot → 0.
     - `48` name. `46` volume text: `"{:.1} dB"` of `fader_db`, `"-inf dB"` at the floor, never `"-0.0"`. `47` pan text: `"C"`, `"L{n}"`, `"R{n}"`, where n is the percentage.

How Task 1's `Kontrol` behaves. Tasks 2 and 3 extend it.
- `hello()` returns `[[BF 01 04]]` and starts the hello timer at the next feedback.
- `input`:
  - It splits the bytes with `midi::split`; every `Err` is counted.
  - `BF 01 v` is the answer: Ruling 4. A second answer while online re-greets: the state refreshes and the name is sent again.
  - `BF 02 xx` while online is `set_online(false)`.
  - Anything else is ignored and counted. Task 2 replaces this arm.
- `feedback(view, first, now)`:
  - Offline, it is empty, except the hello repeat.
  - Online, it is the identity once after each accepted answer. Task 3 adds the rest.
  - It always records `view` and `first`, so Task 2's input can address strips.
- `goodbye()` is `[[BF 02 00]]` and sets the unit offline. Task 3 adds the empty slots.
- `release_all` returns `Held { touched: vec![], idle: idle.take_all() }` and sets the unit offline. `release_holds` does the same and stays online. `touched()` is empty: the keyboard reports no touch. `refresh()` clears the cache.
- `Kontrol` implements the crate's `Unit` trait (`link`, `idle`, `forget_all`), so going offline answers the releases.

`Kontrol` input follows Ruling 5. It keeps what the last feedback showed:
- the strip ID order of `view.strips`;
- `first`;
- the 8 shown `StripView`s;
- the shown `PluginPageView`, kept only while in Plug-in mode.

The relative "current" of a knob is its idle touch's last value while that touch is open, else the shown value. The new value is `(current + f64::from(steps) * KNOB_STEP).clamp(0.0, 1.0)`. Clicks are `mcu::click(t, mcu::toggled(on))`; make those two `pub(crate)` if they are not.

fn volume_and_pan_knobs_ride_the_shown_strips_and_release_after_idle() {
    assert_eq!(KNOB_STEP, 0.005);
    let (mut k, now) = online(&view(10), 2);
    let later = now + Duration::from_millis(100);
    assert_eq!(
        k.input(&[0xBF, 0x50, 0x05], now),
        vec![A::Gesture(
            T::StripFader(StripId(3)),
            Phase::Touch(Some(0.5 + 5.0 * KNOB_STEP))
        )]
    );
    assert_eq!(
        k.input(&[0xBF, 0x50, 0x7B], later),
        vec![A::Gesture(
            T::StripFader(StripId(3)),
            Phase::Value(0.5 + 5.0 * KNOB_STEP + -5.0 * KNOB_STEP)
        )]
    );
    assert_eq!(
        k.input(&[0xBF, 0x59, 0x7F], now),
        vec![A::Gesture(
            T::StripPan(StripId(4)),
            Phase::Touch(Some(0.5 + -1.0 * KNOB_STEP))
        )]
    );
    assert_eq!(
        k.input(&[0xBF, 0x57, 0x3F], now),
        vec![A::Gesture(
            T::StripFader(StripId(10)),
            Phase::Touch(Some(0.5 + 63.0 * KNOB_STEP))
        )]
    );
    for _ in 0..10 {
        let _ = k.input(&[0xBF, 0x57, 0x3F], now);
    }
    match k.input(&[0xBF, 0x57, 0x3F], now).as_slice() {
        [A::Gesture(_, Phase::Value(v))] => assert_eq!(*v, 1.0, "clamped"),
        other => panic!("{other:?}"),
    }
    assert!(k.input(&[0xBF, 0x50, 0x00], now).is_empty(), "no movement");
    assert_eq!(k.ignored(), 0);
    let rel = k.tick(later + IDLE_RELEASE);
    assert!(rel.contains(&A::IdleRelease(T::StripFader(StripId(3)), later)));
    assert!(rel.contains(&A::IdleRelease(T::StripPan(StripId(4)), now)));
    assert!(rel.contains(&A::IdleRelease(T::StripFader(StripId(10)), now)));
}

fn drives_the_mixer_from_a_kontrol_mk3() {
