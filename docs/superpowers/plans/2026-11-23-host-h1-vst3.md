# 27.1.0 Host Track H1: VST3 Hosting Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** VizDAW hosts VST3 plug-ins on macOS and Linux behind the existing `PluginInstance` seam: scan and catalogue, load, process audio and MIDI, parameters and automation, latency, sidechain, state save/restore, faults — proven with the VST3 SDK's sample plug-ins and a small in-repo Rust test VST3, with the song-format bump the owner ruled for VST3 slots. Editors are H2.

**Architecture:** A `core-host/src/vst3/` module on the `vst3` crate (coupler-rs, MIT/Apache, pinned `=0.3.0`, pre-generated bindings, host-side COM in Rust): module loading (`libloading`, bundle resolution on macOS and Linux), factory and class info, `Vst3Instance: PluginInstance` (component + controller, connection points, `IComponentHandler`), `Vst3Processor: AudioProcessor` (preallocated `ProcessData`, event and parameter-change lists over fixed arrays, `ProcessContext`), and a two-stream state blob. `PluginFormat::Vst3` joins `Au` and `Clap` across the model, scanner, catalogue and DAWproject import/export.

**Tech Stack:** Rust 2024; `vst3 = "=0.3.0"`, `libloading`; VST3 SDK sample plug-ins (MIT) built in CI; the existing `test-plugins` crate.

**Spec:** `docs/superpowers/specs/2026-11-20-cross-platform-27-1-design.md` (§2 goal 4, §2b owner ruling: VST3 slots bump the song format), `docs/superpowers/specs/2026-10-16-plugin-hosting-design.md`, backlog row "VST3 hosting". Research notes with citations: the host-track inventory (§1, §2, §5, §6 H1). H0 plan and Outcome (run loop, rulings): `docs/superpowers/plans/2026-11-23-host-h0-clap-linux.md`.

## Global Constraints

- This track works in the worktree `~/workspace/vizdaw-host` on branch `host`; it never edits `crates/vizdaw-gpui` or `crates/vizdaw-app` (the mixer track owns them).
- No allocation or locking on the audio thread (`rt_alloc_plugins` with a VST3 plug-in proves it). Plug-in main-thread calls only on the main thread; calls a plug-in makes to the component handler from the audio thread are queued to the main thread.
- Song format: a document containing a VST3 slot bumps the song format under the usual migration rules (owner ruling §2b); documents without VST3 slots are written as before if the format rules allow, else a plain bump with a no-op migration — decide in Task 1 against the existing migration code and record the ruling.
- macOS behaviour for AU and CLAP unchanged. The Swift beta is not a compatibility target (owner 2026-11-23): no file or catalogue compatibility with it, and uniffi changes need not stay additive; report any Swift build breakage rather than working around it.
- Licence notices: the VST3 SDK (MIT) and the `vst3` crate (MIT/Apache) go through `scripts/third-party-notices.sh`; licence notices may name the copyright holders (owner ruling). Banned vendor/DAW names stay out of other repo text.
- In-process hosting (plug-ins in the app process); the scanner stays out of process.
- Subagents: no GUI, no computer-use, never `dangerouslyDisableSandbox`. Linux runs by the controller over SSH (`~/vizdaw-host`) or in CI.
- CI: fmt, clippy `-D warnings`, tests on macOS and Linux. Commit trailers as before.

## Review Focus

1. COM lifetimes: release order (view, controller terminate, component terminate, module exit); single-component vs split plug-ins; a plug-in that fails mid-initialise leaves nothing loaded.
2. Audio thread: no allocation/locks; component-handler calls from the audio thread queued, not executed there.
3. State: save → load round-trips component and controller state; a damaged blob refuses cleanly; a project with a VST3 slot opened by an older build is refused (format bump).
4. Scanning: a crashing or hanging VST3 during scan is isolated by the out-of-process scanner and reported; a bundle with several classes lists each.
5. Parameters: normalised↔plain conversion, read-only/hidden flags, step counts, automation and gestures through the existing seam; MIDI CC/pitch bend/aftertouch reach plug-ins via `IMidiMapping`.

### Task 1: model — `PluginFormat::Vst3` and the song format

**Files:** core-model plug-in format enum and every exhaustive match (inventory §1.2), DAWproject import/export, `mixer_chores` text id `vst3:`, migration code; tests in the affected crates.
- [ ] Tests first (format round-trip, a VST3 slot bumps the format, older-format refusal, DAWproject VST3 devices map to slots); implement; record the format-bump ruling in the plan; commit `model: VST3 plug-in format and the song-format bump`.

**Ruling 1 (Task 1, format bump):** a plain bump to song format 12 with a no-op `migrate_v11_to_v12`, for every document. `file::to_json` always writes `VERSION` and the fast load path takes only `VERSION`; every bump since v3 is a plain one with a no-op step. Writing v11 for songs without a VST3 slot would make the writer know what each later version adds, and every later bump would compound it. An older build refuses any v12 song with its `NewerFormat` message (the Swift build is personal-only, owner §2b).

**Ruling 2 (Task 1, spelling):** `PluginFormat::Vst3` is `"vst3"` in files; the slot ID is the class ID as 32 upper-case hex digits (`core_model::mixer::vst3_class_id` normalises either case). The text ID is `vst3:<class ID>`. DAWproject `Vst3Plugin` devices map to slots (the instrument and effects, the EQ tag included), with the ID normalised the same way; only `Vst2Plugin` stays left out (the label is now "VST2 plug-ins"). A VST3 state travels as is in a `plugins/NNN.vstpreset` entry, so Task 5's blob should be in `.vstpreset` layout (class ID plus component and controller chunks), or the DAWproject code must convert it then.

### Rulings

- Task 1: Ruling (implementer, recorded in plan): plain bump to song format 12 with a no-op v11→v12 migration for every document (format code writes one VERSION; per-document versions unsupported) — consequence: an older build (e.g. the owner's Swift beta from main) refuses ANY song saved by a v12 build, not only VST3 songs — surfaced to the owner
- Task 1: Ruling: core-control plugin_ref accepts vst3: (else Co-Producer drops VST3); Swift got two one-line .vst3 cases in exhaustive switches — keeps builds compiling — none
- Task 2: Ruling: VST3 entries in plugins.json (owner change); VST3 discovery off by default (CatalogConfig.include_vst3) until hosting lands — safe default — turn on in Task 6/merge
- Task 2: Ruling: in-repo Rust test VST3 instead of the SDK sample for now; notices script exception for com-scrape-types (no licence file) with vendored licence texts — CI needs it — none
- Task 2: Ruling: the vst3 crate's binding module is named after the SDK vendor; it may appear only in Rust use paths (forced by the crate), never in UI text or strings — carry to Task 3: confine it to one re-export in vst3/ffi.rs
- Task 3: Ruling: instances hold the module by Rc (main-thread only, not Send) — matches the main-thread rule — an instance moved off-thread would not compile (fine)
- Task 3: Ruling (implementer, fix round 1): never unload a VST3 library on any platform (ManuallyDrop; exit still once after releases) — Linux pthread-key TLS destructors from plug-ins outlive dlclose; macOS images already stay loaded — a little memory per distinct plug-in for the process lifetime
- Task 3: Ruling: CLAP libraries also unloaded by clack-host — the macOS-unchanged constraint existed for the Swift build, now retired (owner) — carry to Task 4: process-lifetime CLAP entry cache (never dlclose) on every platform, with the same thread-exit test for the CLAP test plug-in — cost: none beyond memory
- Task 4: Ruling (implementer deviation, accepted by review): controller edits routed by where the component reads next at drain time, not by the state when made — made-time routing loses an edit made while active but drained after deactivation — none (no double apply)
- Task 5: Ruling: residual race (engine dropping a processor on another thread mid-load) accepted — processors are dropped on the main thread in normal operation; worst case one stale value — none practical
- Task 6: Ruling: turn VST3 discovery on by default (include_vst3 true) in Task 6 — the scanner now activates and processes a block before Ok (Task 4), state works (Task 5) — cost: a misbehaving VST3 that passes one block could still crash in use (same as CLAP)
- Task 6: Ruling (naming rule): the SDK source URL contains the vendor's organisation name — allowed only in licence notices; the build script must read it from the notice folder (scripts/licence-texts/vst3sdk/SOURCE) instead of naming it — fix round 1
- Final: Ruling: all task rulings stand (reviewer agrees); declined-to-judge items (pre-existing host behaviour for every format; Windows not a target; main-thread module loading per plan) stand
